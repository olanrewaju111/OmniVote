     2→// PostgreSQL-Ready Schema for OmniVote Monitor v2.1
     3→// =============================================================================
     4→//
     5→// This is the PostgreSQL-ready version of the Prisma schema.
     6→// To migrate from SQLite to PostgreSQL:
     7→//
     8→//   1. Replace the contents of prisma/schema.prisma with this file
     9→//   2. Ensure DATABASE_URL is set to a PostgreSQL connection string, e.g.:
    10→//        DATABASE_URL="postgresql://user:password@localhost:5432/omnivote"
    11→//   3. Run: npx prisma migrate dev --name init_pg
    12→//   4. Restart the application
    13→//
    14→// SQLite → PostgreSQL differences to review:
    15→//   - DateTime: SQLite stores as TEXT (ISO-8601 string); PostgreSQL uses TIMESTAMP.
    16→//     Prisma handles this transparently, but existing data must be migrated
    17→//     with compatible date format strings.
    18→//   - Boolean defaults: SQLite uses 0/1 integers for booleans; PostgreSQL uses
    19→//     true/false. The Prisma migration will handle the conversion, but verify
    20→//     any raw SQL queries that reference boolean columns.
    21→//   - String defaults: SQLite @default("") maps to TEXT NOT NULL DEFAULT '';
    22→//     PostgreSQL handles this the same way, but JSON columns stored as String
    23→//     may benefit from native JSON/JSONB types in a future optimization.
    24→//   - CUID generation: @default(cuid()) works on both databases.
    25→//   - Auto-increment: Not used in this schema; all IDs use cuid().
    26→//   - Connection pooling: Consider using PgBouncer or Prisma Accelerate for
    27→//     production PostgreSQL deployments.
    28→// =============================================================================
